## 3. Retrospectiva Ágil (Lo que Funcionó, Desafíos y Aprendizajes)

### 🟢 ¿Qué funcionó muy bien?
1. **Modelado con Java 21 Records**: Los DTOs inmutables eliminaron por completo el código boilerplate de getters/setters y garantizaron que los datos recibidos de la API no puedan ser alterados en memoria.
2. **Consultas con `JOIN FETCH`**: La implementación de `searchCatalog` en `ProductRepository` cargó las categorías en una sola consulta SQL, erradicando el problema de rendimiento N+1.
3. **Pipeline de GitHub Actions**: La integración continua automatizada detectó tempranamente discrepancias de base de datos antes de fusionar código a producción.

### 🔴 Desafíos Encontrados y Soluciones Técnicas (Bitácora de Ingeniería)

#### Desafío 1: Acoplamiento de `@EnableJpaAuditing` en Pruebas Web (`@WebMvcTest`)
- **Problema**: Al correr `@WebMvcTest(ProductController.class)`, el contexto falló con `BeanCreationException: Cannot resolve reference to bean 'jpaMappingContext'`.
- **Causa Raíz**: `@EnableJpaAuditing` estaba colocada en `StockPilotApplication.java`. Como `@WebMvcTest` deshabilita los componentes JPA para ser rápido (< 1s), el auditor de JPA no encontró el contexto de mapeo.
- **Solución Aplicada**: Se extrajo `@EnableJpaAuditing` a una clase de configuración dedicada `JpaConfig.java`. De este modo, los slice tests web ignoran la configuración JPA y ejecutan en milisegundos de forma limpia.

#### Desafío 2: Restricción de Identidad en PostgreSQL (`GENERATED ALWAYS` vs `BY DEFAULT`)
- **Problema**: En GitHub Actions, la migración `V11` falló porque PostgreSQL arrojó `PSQLException: cannot insert a non-DEFAULT value into column "id"`.
- **Causa Raíz**: Las tablas V1-V9 usaban `GENERATED ALWAYS AS IDENTITY`, lo que impide que scripts DML inserten IDs fijos requeridos para las claves foráneas de los datos semilla.
- **Solución Aplicada**: Se modificó a `GENERATED BY DEFAULT AS IDENTITY` y se agregaron llamadas a `setval(pg_get_serial_sequence(...))` para sincronizar las secuencias tras la inserción manual.
